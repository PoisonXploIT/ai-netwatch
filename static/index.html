Guía de uso

Qué es y qué ve (y qué NO ve)

AI NetWatch monitoriza las conexiones salientes hacia proveedores cloud IA (catálogo de ~20 dominios: OpenAI, Anthropic, Google, TypeSafe/Jev, Groq, DeepSeek, Hugging Face...). De cada conexión ve:

  • Proceso que abre la conexión (+ruta completa con Sysmon).
  • Destino IP:puerto y protocolo (TCP/UDP).
  • Dominio real por SNI (tshark): el dominio declarado en el handshake TLS, inmune a CNAME/CDN.
  • Catálogo: match contra dominios IA conocidos (resolución activa cada 5 min).
  • IA (capa): cómo se clasificó el dominio — catálogo (evidencia), heurística (señal a revisar, TLD .ai/token IA), LLM local (bajo demanda) o sin clasificar. Cobertura universal: un proveedor no listado se ve si resolvio DNS (EID 22).
  • Periodicidad (veces observado) y primera/última vez.

Bytes remotos: opt-in (v2.2). El trafico TLS viaja cifrado, asi que no se ve el contenido; el volumen (cuanto sale) SI se mide con un colector elevado (ETW Kernel-Network), desactivado por defecto. El egress en bytes del LLM local se mide siempre via el proxy inspector. QUIC/HTTP-3 (UDP 443) se cubre por SNI (v2.5).

Fuentes de datos
  • Polling (5 s): TCP establecidas (Get-NetTCPConnection) + UDP conectados (netstat -ano -p UDP). Puede perder conexiones muy breves (<5 s). Limite medido: netstat no lista UDP IPv6.
  • Sysmon (EventID 3): cada conexión TCP es un evento; aporta la ruta completa del proceso (detecta masquerading: p. ej. svchost.exe fuera de System32). Recomendado. No cubre QUIC/UDP.
  • tshark (SNI): dominio real por handshake TLS y QUIC/HTTP-3 (udp port 443 or tcp port 443; el SNI sale del paquete Initial de QUIC). Solo en sesiones nuevas; una keep-alive ya establecida no repite SNI.
  • Sysmon (EventID 22, DnsQuery): proceso + dominio consultado + IPs resueltas; cobertura universal (R1) y alimenta dns_resolutions.
  • Sysmon (EventID 1): creacion de proceso (imagen + CommandLine) para el linaje (autonomia R2) y el fingerprint de SDK.
Filtros y agrupación de eventos (v2.3)

La tarjeta Eventos tiene una fila de filtros: capa IA, autonomía, solo no aprobados, ocultar CDN, proceso/destino y botón Limpiar. Con Agrupar por proveedor (on por defecto) cada fila es un par (proceso, proveedor): colapsa las IPs rotatorias de CDN (p. ej. python.exe → huggingface.co: 104 IPs en una fila) sumando sesiones/polls y contando IPs distintas. Cada fila lleva provider + kind (API/web/CDN).

Shadow AI (v2.0)

La tarjeta Shadow AI lista la IA detectada que no está aprobada. Aprobado = el catálogo (por defecto) + los proveedores que apruebes ahí (match por sufijo de dominio: aprobar openai.com cubre api.openai.com). Cada proveedor no aprobado dispara la alerta shadow_ai. Config: catalog_approved y approved_providers. Es gobernanza (qué IA permites), distinta de la detección.

Veredictos Jev (triage)

El botón Triar eventos con Jev envía los eventos vivos a Jev (TypeSafe, modelo pin) y obtiene por cada uno:

  • Uso IA esperado (expected_ai_use): uso legítimo de un servicio IA.
  • Exfiltración sospechosa (background_exfil_suspect): salida sin acción de usuario, horario extraño o periodicidad tipo telemetría. Revisar primero.
  • Telemetría / ruido (telemetry_noise): pings pequeños de baja sensibilidad.
  • No relacionado (unrelated): falso positivo del catálogo (p. ej. IP compartida de CDN).

Métricas: confianza (0-1), prob. falso positivo = 1 - confianza (v2.4), criticidad 0-3 y acción inmediata (0-1). El triaje cubre todos los eventos, en lotes de 50 por llamada. Coste ~$0.001-0.002 por lote.

Explicaciones técnicas (LLM local) — qué hace y qué NO hace

Si el LLM local está configurado, los eventos marcados (criticidad ≥2 o no-expected) reciben una explicación en español: qué es, por qué importa y sugerencia. El LLM solo loopback, sin API key y nunca re-scorea el veredicto de Jev: es un explicador, no un detector ni un juez. Solo se llama tras Jev, solo sobre eventos ya marcados, y si falla todo sigue funcionando. Ademas, el boton Investigar con LLM local (v2.4) pide a demanda que confirme/refute/complete un veredicto de Jev (o lo evalue si aun no se trio): devuelve {evaluacion: confirm|refuta|insuficiente, porque, evidencia_faltante}. Sigue siendo asesoria display-only: no re-puntua; Jev sigue siendo el juez.

LLM Inspector (R3)

Un reverse proxy stdlib en 127.0.0.1 (puerto configurable, por defecto 8098) reenvía al LLM local (target configurable, solo loopback). Como ambos extremos son loopback y HTTP plano, el inspector ve toda la llamada en claro: prompt completo, respuesta, modelo, tokens (si el servidor los reporta), latencia y si era streaming.

  • Cómo usarlo: activa el toggle y apunta el cliente al puerto del proxy (p. ej. http://127.0.0.1:8098 en vez de :8099).
  • Cobertura: chat/completions (incluido tool-calling), embeddings, audio e imágenes. Un intento que no conecta al upstream queda registrado como fallo (HTTP sin respuesta). Embeddings e imágenes no persisten el dato crudo: solo metadatos.
  • Auto-observación: si la URL del LLM local apunta al mismo upstream que el target del proxy, las llamadas propias de NetWatch (explicador y test) también pasan por el proxy y quedan registradas. La config no se reescribe; el proxy nunca apunta a sí mismo.
  • Enlace local: cada llamada intenta enlazarse con el evento de red del mismo destino, proceso y ventana temporal (120 s), si ese destino está siendo vigilado.
  • Límite honesto: solo cubre el LLM local. Un proveedor remoto (TLS) no se puede descifrar pasivamente; de él se ve la conexión (eventos de red) pero no el contenido.
  • Privacidad: prompts y respuestas quedan en claro en data/llm_calls.db. Si un prompt lleva una API key o datos sensibles, esa información queda en ese fichero: borra las llamadas cuando termines (botón de la tarjeta).
Fingerprint de SDK IA (v2.3)

Por cada proceso, NetWatch mira si su runtime lleva un SDK de IA instalado: en Python, paquetes en site-packages (openai, anthropic, langchain, huggingface-hub, litellm, ollama...); en Node, node_modules local o global. Identifica qué cliente es sin depender del dominio. Si no hay artefacto verificable, no inventa (queda sin etiqueta). Fuente: Sysmon EID 1 (imagen + CommandLine). Endpoint GET /api/processes; el Panel muestra "Procesos con SDK IA". Es display-only.

Bytes remotos (v2.2)

netcollector.py es un colector elevado (UAC, opt-in) que traza Microsoft-Windows-Kernel-Network con logman/tracerpt y suma bytes por destino (solo copia de datos TCP/UDP; sin loopback ni DNS). El servidor no elevado solo lee el JSONL resultante. Config: net_bytes_enabled (off por defecto), net_bytes_duration_s, net_bytes_cycle_s. Con datos, el panel muestra cloud_bytes real; sin admin o sin datos, "no disponible" con motivo — nunca un cero que engane. Elevación sin prompt (v2.2.1): una vez creada la tarea programada AI-NETWATCH-NetBytes (setup único elevado, setup_netbytes_task.ps1), cada ciclo se dispara con schtasks /run: sin UAC por ciclo y funciona aunque el servidor corra oculto. Sin la tarea, degrada al UAC por ciclo (solo consola interactiva). El panel muestra spawn_method (task/uac) y last_meta para distinguir "corrió y no hubo tráfico" de "falló".

Reglas (v2.2)

El motor de reglas evalía cada 60 s el estado existente: service_ai_call (veredicto autónomo/programado llamando a IA no aprobada), beacon_unapproved (beaconing a proveedor no aprobado) y egress_volume_unapproved (>X MB a IA no aprobada según bytes remotos; sin datos de colector, disponible=false). Cada regla que pasa a disparar genera una alerta rule_fired; la tarjeta muestra su estado en vivo.

Sesiones y beaconing (F1/D3)

La columna Sesiones cuenta episodios de conexión, no polls: una sesión es una transición ausente→presente por (proceso, IP, puerto). Un keep-alive largo que sigue presente sigue siendo 1; un reconnect suma. El badge beacon marca beaconing: periodicidad regular (CV de inter-arrival ≤0.3 con ≥5 sesiones) — patrón típico de C2, no de keep-alive. Dispara la alerta beaconing_ai_call (una por clave IA).

Autonomía (R2)

Cada evento IA lleva un veredicto persistido: usuario, autónomo o programado. Señales: sesión bloqueada/pantalla apagada, usuario inactivo, foreground y linaje del proceso (padre servicio/tarea programada vía Sysmon EID 1). El triaje Jev recibe el estado real del usuario (user_active), y una salida autónoma/programada dispara la alerta autonomous_ai_call. Sin señales disponibles, el veredicto queda unknown: nunca se inventa.

Estadísticas y reset

El histórico diario (eventos/triajes por día) se conserva incluso tras el reset: Empezar de cero borra solo los eventos y triajes vivos. La vista de 7 días (o hasta 365 en la API) lee de ese histórico.

Exportación (JSON / CSV / PDF / Evidence)
  • JSON: eventos completos + último triaje (estado, veredictos, explicaciones LLM).
  • CSV: una fila por evento (proceso, ruta, protocolo, IP:puerto, SNI, catálogo, veces, fechas).
  • PDF: informe con cabecera, eventos, último triaje Jev y estadísticas de 7 días.
  • Evidence (v2.3): /api/evidence/chain (JSONL con cadena de hashes: si se altera una fila se rompe el resto, verificable offline) y /api/evidence/stix (bundle STIX 2.1 para SIEM/CTI). Con selector de ventana en días.

Todo se genera en memoria; ningún endpoint toma nombres de archivo del usuario (sin path traversal).

Configuración
  • Jev (TypeSafe): API key para el triaje. El endpoint y el modelo están fijados (no configurables por la API).
  • LLM local: URL + modelo de un servidor OpenAI-compatible. Solo se aceptan URLs loopback absolutas; sin API key.
  • Hosts extra: IPs o dominios propios que quieras vigilar además del catálogo IA.
  • Sysmon / tshark: toggles en vivo (sin reiniciar).

La configuración es persistente (data/config.json) y se revalida al cargar: un archivo editado a mano no puede activar una URL peligrosa.

Seguridad y privacidad
  • Solo loopback: el servidor escucha únicamente en 127.0.0.1:8790; no hay superficie externa ni auth.
  • SSRF: la única salida HTTP a destino elegido por el usuario es llm_base_url, que debe ser http(s) absoluto resolviendo a loopback. Público, metadata cloud (169.254.169.254), file://, gopher:// y rutas relativas → 400.
  • Sin payload: la captura SNI es pasiva (solo el dominio del handshake); no se guarda contenido de ninguna conexión.
  • Reset protegido: exige {"confirm": true}.
  • Exports sin secretos: JSON/CSV/PDF nunca incluyen la API key ni la config.
