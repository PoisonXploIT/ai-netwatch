Guía de uso

Qué es y qué ve (y qué NO ve)

AI NetWatch monitoriza las conexiones salientes hacia proveedores cloud IA (catálogo de ~20 dominios: OpenAI, Anthropic, Google, TypeSafe/Jev, Groq, DeepSeek, Hugging Face...). De cada conexión ve:

  • Proceso que abre la conexión (+ruta completa con Sysmon).
  • Destino IP:puerto y protocolo (TCP/UDP).
  • Dominio real por SNI (tshark): el dominio declarado en el handshake TLS, inmune a CNAME/CDN.
  • Catálogo: match contra dominios IA conocidos (resolución activa cada 5 min).
  • IA (capa): cómo se clasificó el dominio — catálogo (evidencia), heurística (señal a revisar, TLD .ai/token IA), LLM local (bajo demanda) o sin clasificar. Cobertura universal: un proveedor no listado se ve si resolvio DNS (EID 22).
  • Periodicidad (veces observado) y primera/última vez.

Bytes remotos: no. El trafico TLS remoto viaja cifrado; de el se ve la conexion y el dominio, no cuanto sale (bytes remotos requieren ETW/Npcap/MITM). El egress en bytes SI se mide para el LLM local (proxy inspector): bytes que salen hacia el LLM y que vuelven.

Fuentes de datos
  • Polling (5 s): conexiones TCP establecidas + endpoints UDP. Puede perder conexiones muy breves (<5 s).
  • Sysmon (EventID 3): cada conexión es un evento, ninguna se pierde; aporta la ruta completa del proceso (detecta masquerading: p. ej. svchost.exe fuera de System32). Recomendado.
  • tshark (SNI): dominio real por handshake TLS. Solo lo ve en sesiones TLS nuevas; una keep-alive establecida antes del arranque no repite SNI.
  • Sysmon (EventID 22, DnsQuery): proceso + dominio consultado + IPs resueltas. Permite enlazar la conexion al dominio real aunque no este en el catalogo (cobertura universal R1).
Veredictos Jev (triage)

El botón Triar eventos con Jev envía los eventos vivos a Jev (TypeSafe, modelo pin) y obtiene por cada uno:

  • Uso IA esperado (expected_ai_use): uso legítimo de un servicio IA.
  • Exfiltración sospechosa (background_exfil_suspect): salida sin acción de usuario, horario extraño o periodicidad tipo telemetría. Revisar primero.
  • Telemetría / ruido (telemetry_noise): pings pequeños de baja sensibilidad.
  • No relacionado (unrelated): falso positivo del catálogo (p. ej. IP compartida de CDN).

Métricas: confianza (0-1), prob. falso positivo (derivada), criticidad 0-3 y acción inmediata (0-1). Coste ~$0.001-0.002 por triaje (batch de hasta 50 eventos).

Explicaciones técnicas (LLM local) — qué hace y qué NO hace

Si el LLM local está configurado, los eventos marcados (criticidad ≥2 o no-expected) reciben una explicación en español: qué es, por qué importa y sugerencia. El LLM solo loopback, sin API key y nunca re-scorea el veredicto de Jev: es un explicador, no un detector ni un juez. Solo se llama tras Jev, solo sobre eventos ya marcados, y si falla todo sigue funcionando.

LLM Inspector (R3)

Un reverse proxy stdlib en 127.0.0.1 (puerto configurable, por defecto 8098) reenvía al LLM local (target configurable, solo loopback). Como ambos extremos son loopback y HTTP plano, el inspector ve toda la llamada en claro: prompt completo, respuesta, modelo, tokens (si el servidor los reporta), latencia y si era streaming.

  • Cómo usarlo: activa el toggle y apunta el cliente al puerto del proxy (p. ej. http://127.0.0.1:8098 en vez de :8099).
  • Cobertura: chat/completions (incluido tool-calling), embeddings, audio e imágenes. Un intento que no conecta al upstream queda registrado como fallo (HTTP sin respuesta). Embeddings e imágenes no persisten el dato crudo: solo metadatos.
  • Auto-observación: si la URL del LLM local apunta al mismo upstream que el target del proxy, las llamadas propias de NetWatch (explicador y test) también pasan por el proxy y quedan registradas. La config no se reescribe; el proxy nunca apunta a sí mismo.
  • Enlace local: cada llamada intenta enlazarse con el evento de red del mismo destino, proceso y ventana temporal (120 s), si ese destino está siendo vigilado.
  • Límite honesto: solo cubre el LLM local. Un proveedor remoto (TLS) no se puede descifrar pasivamente; de él se ve la conexión (eventos de red) pero no el contenido.
  • Privacidad: prompts y respuestas quedan en claro en data/llm_calls.db. Si un prompt lleva una API key o datos sensibles, esa información queda en ese fichero: borra las llamadas cuando termines (botón de la tarjeta).
Estadísticas y reset

El histórico diario (eventos/triajes por día) se conserva incluso tras el reset: Empezar de cero borra solo los eventos y triajes vivos. La vista de 7 días (o hasta 365 en la API) lee de ese histórico.

Exportación (JSON / CSV / PDF)
  • JSON: eventos completos + último triaje (estado, veredictos, explicaciones LLM).
  • CSV: una fila por evento (proceso, ruta, protocolo, IP:puerto, SNI, catálogo, veces, fechas).
  • PDF: informe con cabecera, eventos, último triaje Jev y estadísticas de 7 días.

Los tres se generan en memoria; ningún endpoint toma nombres de archivo del usuario (sin path traversal).

Configuración
  • Jev (TypeSafe): API key para el triaje. El endpoint y el modelo están fijados (no configurables por la API).
  • LLM local: URL + modelo de un servidor OpenAI-compatible. Solo se aceptan URLs loopback absolutas; sin API key.
  • Hosts extra: IPs o dominios propios que quieras vigilar además del catálogo IA.
  • Sysmon / tshark: toggles en vivo (sin reiniciar).

La configuración es persistente (data/config.json) y se revalida al cargar: un archivo editado a mano no puede activar una URL peligrosa.

Seguridad y privacidad
  • Solo loopback: el servidor escucha únicamente en 127.0.0.1:8790; no hay superficie externa ni auth.
  • SSRF: la única salida HTTP a destino elegido por el usuario es llm_base_url, que debe ser http(s) absoluto resolviendo a loopback. Público, metadata cloud (169.254.169.254), file://, gopher:// y rutas relativas → 400.
  • Sin payload: la captura SNI es pasiva (solo el dominio del handshake); no se guarda contenido de ninguna conexión.
  • Reset protegido: exige {"confirm": true}.
  • Exports sin secretos: JSON/CSV/PDF nunca incluyen la API key ni la config.
